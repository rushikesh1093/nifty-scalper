# study_phase=False, EMA/RSI strategy fixes, signal-to-trade pipeline unblocking

This change tears out the study_phase blockage that was preventing all paper trades from executing, fixing a server_default of `"true"` in migration 0005 that silently set every new deployment into observe-only mode. `ensure_config()` in `mode_manager.py` now force-resets any existing row that has `study_phase=True` on startup, providing a belt-and-suspenders recovery path. Two strategies (`EMAVWAPStrategy` and `RSIVWAPStrategy`) received logic fixes that were independently preventing signals from firing: EMA was redundantly recomputing full arrays when indicators already had the latest values, and RSI had overlapping thresholds at the 70/72 boundary that could suppress momentum signals. The migration adds an `UPDATE` to fix any already-deployed row.

Watch for: **(confirmed)** `ensure_config()` is called before `strategy_runner.start()` in `main.py`, but `strategy_runner.start()` internally calls `paper_engine.start()` which starts the monitor loop — if `ensure_config()` raises, the warning log at the bottom of startup still tries to read `cfg.study_phase`, which is a second DB call that could also fail silently. **(confirmed)** `EMAVWAPStrategy` still recomputes the full EMA array on every candle tick to get `[-2]`; with 500 candles this is O(n) per tick per strategy. **(confirmed)** `RSIVWAPStrategy` reversal SELL threshold at RSI>72 is above the RSI>70 overbought convention — fine if intentional, but the momentum BUY block at `70 < rsi_cur <= 72` only has a 2-point window, which will rarely trigger. **(likely)** The `ensure_config()` fix lands in the DB, but if `strategy_runner.start()` runs while `reconcile_used_capital()` is still in-flight (both are `await`ed sequentially, so this is actually safe) there is no issue — but the `_eod_monitor` task's pre-market reset at 9:00 does NOT call `ensure_config()`, so a row flipped to `study_phase=True` via the API mid-session would stay that way until the next full restart.

**Verdict**: NEEDS_CHANGES

## High-level view

The study_phase migration fix is correct and well-defended: `server_default` changed to `"false"`, the migration UPDATE covers existing rows, and `ensure_config()` covers the app restart path. The one gap is that the API-level guard on `study_phase` is missing — `update_config()` accepts `**kwargs` without filtering, so a caller can `PATCH /trading/config {"study_phase": true}` and re-engage the block at any time without any protection or warning.

The `EMAVWAPStrategy` fix correctly avoids double-computing the full EMA at [-1] by reading from `indicators`, but still recomputes the full O(n) EMA array for the [-2] crossover check. Given that `compute_all` already runs every indicator once per cycle and shares the result across all 12 strategies, the right fix is to store the prior-bar value in `compute_all` (e.g. `ema9_prev`, `ema21_prev`). This is a performance concern, not a correctness bug — signals fire correctly today, just at the cost of extra numpy work each tick.

The RSI threshold redesign (reversal SELL at >72, momentum BUY at 70–72) eliminates the ambiguity at the original boundary, but the 2-point window (70–72) for the momentum BUY tier is very narrow and will rarely produce signals on real Nifty data. More practically, the reversal SELL at >72 means the first time RSI crosses above 70 and is near VWAP, no signal fires until it reaches 72, which is a meaningful tightening for an overbought reversal setup. The downside momentum SELL at RSI<30 with a 3-bar trend requirement is appropriately tight.

The signal-to-trade pipeline has four non-`study_phase` blockers that survive this change: the AngelOne session validity check before going live (`switch_to_live`), the option hard filters (OI < 1L, volume < 5k, spread > 2%), the minimum score gate (≥ 40/100) in `OptionSelector`, and the `SignalAggregator` 3-minute same-direction cooldown. Any of these can silently suppress trades without a signal ever reaching `PaperEngine`. The only one that surfaces to the caller is the mode_manager's `pre_trade_check`, which logs `SKIPPED` with a reason. The option selector's rejections are logged at DEBUG level and will be invisible unless logging is turned up.

The `_eod_monitor` task runs a `while True` loop checking IST time every 30 seconds. At 15:15 it calls `_eod_square_off`, which fetches all open positions from the DB and closes them by calling `paper_engine._close_position` directly, bypassing the monitor loop's `_check_position` path. If `_close_position` is called simultaneously by both the monitor loop and `_eod_square_off` for the same position, the early `not pos.is_open` guard prevents a double-close, but `mode_manager.on_position_closed` releases capital twice — `_close_position` calls it unconditionally after the DB update, and the monitor loop may have already called it for the same position in the same second.

<summary>Issues (7)</summary>

1. **`update_config()` accepts `study_phase=True` unchecked** — `update_config(**kwargs)` in `mode_manager.py` applies any field without validation. A caller can re-engage study_phase via the API and block all trades with no warning. Add an explicit guard that rejects or logs loudly if `study_phase=True` is passed.

2. **Double capital release on EOD square-off** — `_eod_square_off` in `strategy_runner.py` calls `paper_engine._close_position(pos.id, ltp, "EOD")`. `_close_position` calls `mode_manager.on_position_closed`. If the `_monitor_loop` (which runs every 1 second) fires at 15:15:00 and also hits the `now_ist >= dtime(15,15)` branch for the same position in the same second, `on_position_closed` is called twice and `used_capital` goes negative. The `max(0.0, ...)` floor in `on_position_closed` contains the accounting damage, but the second release still logs a misleading capital release event. Fix: check `is_open` inside `_check_position` under a DB read-then-update, or coordinate EOD square-off to cancel the monitor task briefly.

3. **Momentum BUY window at RSI 70–72 is too narrow** — A 2-point band that also requires 3 consecutive bars of rising RSI will very rarely fire on 1-minute Nifty data. RSI oscillates; sustained linear increases across 3 bars within a 2-point window require near-tick precision. Consider widening the lower bound to 65 or extending the band.

4. **O(n) EMA recompute inside `EMAVWAPStrategy.evaluate()`** — `ema(c_arr, 9)` and `ema(c_arr, 21)` are recomputed on the full candle array (up to 500 candles) every tick to get `[-2]`. `compute_all` already computes these arrays once and shares the scalar `[-1]`. Store `ema9_prev` and `ema21_prev` in `compute_all` so strategies can read `[-2]` from `indicators` without recomputing. Same issue exists in `BollingerBreakoutStrategy` (recomputes full `bollinger` array) and `RSIVWAPStrategy` (recomputes full `rsi` array).

5. **Option selector rejections logged at DEBUG** — Hard filter rejections in `score_candidate` and soft filter below-MIN_SCORE rejections in `_build_candidates` both log at `DEBUG`. In the default `INFO` production log level these are completely invisible. If trades are not firing because no options pass the 100k OI / 5k volume / 2% spread gates, nothing surfaces to the operator. Promote hard filter rejections to `INFO` or add an `INFO`-level summary line per signal showing how many candidates were rejected and why.

6. **`ensure_config()` is not called in `_eod_monitor`'s 9:00 pre-market path** — `_pre_market_setup()` calls `reset_daily_counter()` and `reconcile_used_capital()` but not `ensure_config()`. If `study_phase` gets set to `True` via the API during the day and the server is not restarted, the only recovery path is a manual API call. This is a minor gap but inconsistent with the "force False on startup" intent.

7. **`daily_pnl_summary` unique index mismatch** — Migration 0002 creates the unique index on `(date, strategy_name)` only (2 columns), but the model defines it on `(date, strategy_name, mode)` (3 columns). `_update_daily_pnl` queries on all three. If multiple modes exist for the same strategy on the same day (e.g., switching PAPER → LIVE intraday), the DB will raise an `IntegrityError` on the second mode because the 2-column index sees it as a duplicate. This is a pre-existing schema bug exposed by any PAPER/LIVE switching workflow.

<summary>Details</summary>

### `update_config()` allows study_phase to be re-engaged silently

`ensure_config()` defends the startup path aggressively — it force-sets `study_phase=False` and logs a warning if it finds `True`. But `update_config(**kwargs)` in `mode_manager.py` is a raw passthrough to the database:

```python
async def update_config(self, **kwargs) -> TradingConfig:
    async with AsyncSessionLocal() as db:
        await db.execute(
            update(TradingConfig).where(TradingConfig.id == 1).values(**kwargs)
        )
```

There is no guard here. Any API route that calls `mode_manager.update_config(study_phase=True)` will silently re-enter observe-only mode. The `trading.py` route file wasn't read, but the pattern exists. The `TradingConfig` model comment says `"cannot be set to True via normal config updates"` — that comment is aspirational, not enforced. Either filter `study_phase` out of `**kwargs` unconditionally, or add a loud warning log when it arrives as `True`.

### Double capital release at 15:15

`_eod_monitor` fires at 15:15 and calls `_eod_square_off`, which iterates open positions and calls `_close_position` on each. `_close_position` unconditionally calls `mode_manager.on_position_closed(pos.trade_amount_used)` after the DB update. The `_monitor_loop` runs every 1 second and at 15:15 will also enter the `now_ist >= dtime(15, 15)` branch in `_check_position`, call `_close_position` for the same position ID. The first call sets `is_open=False`; the second call hits the early return `if not pos or not pos.is_open: return`. Capital release for the first call has already fired. The second call returns before the capital release. So the double-release only materialises in the narrow race window between the monitor loop's `await self._check_position` and the DB write in `_close_position`. Since both tasks are running on the same asyncio event loop and neither yields between the `is_open` check and the `on_position_closed` call, this race requires hitting the exact same `await asyncio.sleep(1)` boundary. It is unlikely but possible, especially on expiry day with many positions closing simultaneously. The `max(0.0, ...)` floor limits accounting damage.

### RSI thresholds for intraday Nifty scalping

For 1-minute Nifty spot candles, standard RSI(14) readings above 70 are genuinely rare and short-lived — during fast trending moves RSI often spikes above 70 briefly then retreats. The reversal SELL threshold raised to >72 means that for the most common overbought scenario (RSI touching 70–72), no reversal signal fires — these are exactly the bars where VWAP rejection trades work best. The momentum BUY block at `70 < rsi_cur <= 72` requiring 3 consecutive rising bars within a 2-point range will statistically fire very few times per day, perhaps near zero. The asymmetry is notable: the oversold side uses RSI<35 (5 points below the standard 30) for reversals and RSI<30 for momentum SELL, giving 5 points of separation. The overbought side uses RSI>72 for reversal SELL and RSI 70–72 for momentum BUY — only 2 points of separation and with the momentum block sitting inside the reversal zone's shadow. The practical effect is that the RSI_VWAP strategy will generate far fewer BUY signals than SELL signals on overbought conditions.

### Pipeline blockers beyond study_phase (confirmed)

The full path a signal must traverse to become a position is:

```
strategy.evaluate()
  → SignalBus.publish()
      → SignalAggregator.should_act()   ← 3-min cooldown gate (in-memory, resets on restart)
          → paper_engine.handle_signal()
              → cfg.study_phase check   ← FIXED by this PR
              → mode_manager.pre_trade_check()
                  → daily loss limit check
                  → max open positions (DB count)
                  → max trades per day (counter)
                  → capital availability
              → option_selector.select()
                  → hard filters (OI/volume/spread/LTP/RR)  ← logged at DEBUG
                  → soft score ≥ 40                          ← logged at DEBUG
```

The `study_phase` fix removes one blocker. The remaining hard stops that can silently kill trades without any `INFO`-level log: hard filter rejections in the option selector (if all 11 candidates across ±5 strikes fail OI or volume thresholds), and the soft score gate below 40. On quiet days or when instrument sync hasn't run recently, the OI/volume fields in Redis ticks will be zero and every candidate will fail filter 3 (OI < 100k). There is no periodic check that verifies tick data is fresh — if the WebSocket feed drops and reconnects without re-subscribing to option tokens, trades will silently stop without any circuit breaker.

### `partial_close` P&L accumulation into gross_pnl

`_partial_close` accumulates `partial_gross` into `pos.gross_pnl`, and later `_close_position` adds `close_gross` on top of `(pos.gross_pnl or 0)`. Since `pos` in `_close_position` is re-fetched from the DB (not the same object), the accumulated value is correct. The brokerage is also accumulated correctly: `partial_brok` is stored in `pos.brokerage` during partial close, and `_close_position` adds `close_brok_now` for the remaining lots. This is fine.

What is not fine: `_partial_close` passes `capital_fraction = partial_qty / pos.quantity` to release proportional capital. If `pos.quantity` is already the reduced value from a prior partial close (because `_partial_close` sets `quantity = remain_qty` in the same UPDATE statement it reads from), the fraction calculation would be wrong. In practice this can't happen because `partial_closed = True` is set in the same UPDATE and `_check_position` skips the partial-close branch when `pos.partial_closed` is True. Still, the logic is order-dependent in a subtle way.
